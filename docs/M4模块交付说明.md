## 修复后的行为

1. 读主档时只采用一次读取的主档原文作为候选状态和冲突基线。另一标签页在读取之后保存了新进度时，当前旧候选的保存会返回 conflict，要求主动重新读取。
2. 读备份之前先记录主档原文。恢复备份过程中若主档发生更新，也不能直接用恢复出的旧进度覆盖更新后的主档。
3. 保存序号采用本服务已经观察到的最高序号，不因读取较旧主档而降低。例如先看到序号 10 的备份、再读取序号 2 的主档，下一次成功保存为 11。
4. 临时档回读完成后、写备份前再次比较主档，及时停止已过期保存，保护此时已存在的新主档及备份。备份后和主档替换前仍保留原有比较。
5. 主档写入后的确认发现内容变化时，返回 conflict；保留当前内存进度，不尝试回滚其他标签页写入的数据。

## 接口与兼容

继续使用 CampusSave.createSaveService(storage, {now?})；storage 实现 getItem、setItem、removeItem。服务暴露 inspect()、save(state)、load('primary' 或 'backup')，CampusSave.parse(raw) 用于独立校验。成功保存返回 ok、savedAt、saveSequence、warning；冲突失败包含 conflict: true、reason。

localStorage 键仍为 bjtu-life:mvp:main、bjtu-life:mvp:backup、bjtu-life:mvp:temporary。外层字段仍为 saveFormatVersion、rulesVersion、appVersion、saveSequence、savedAt、state。完整状态、事件队列、去重标记、经历和随机数位置一起恢复，保存和读取不推进规则状态。

本次未改变接口形状、存档结构、玩法数值或稳定 ID，既有同规则、同格式有效存档可继续使用。未单独调整 M3 主责的 config.js 程序版本；正式发布如需标记新程序版本，由发布人与 M3 统一安排，并记录实际发布提交。

## 已知限制

localStorage 多键写入不具备事务能力。本次增加比较以减少覆盖风险，仍无法完全消除“最后一次比较与实际写入之间”的跨标签竞态。页面 storage 提示和保存冲突检查需要继续配合使用，不将本次修复描述成多标签原子锁。

当前仅保留一个主档和一个上一有效主档备份。临时档不自动升级为主档，备份恢复由玩家主动选择。浏览器清理站点数据或更换源地址会影响存档可用性；没有云同步和跨设备恢复。本次未执行 git 提交、远程推送或正式发布。
